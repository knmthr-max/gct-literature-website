# Decision: サイト内検索に Pagefind を採用する(設計まで。実装は未着手)

- Date: 2026-09-30
- Status: proposed(設計と試作での検証まで完了。実装はこれから)
- 改訂: 2026-10-01(検索語の扱いを「単語ごとのAND/OR/NOT」に改め、原因分析と代替案を追記)
- 試作コード: [`2026-09-30_pagefind_spike/build_index.mjs`](2026-09-30_pagefind_spike/build_index.mjs)

## 1. 目的と制約

公開件数が増えても、次の3つを両立させる。

1. 抄録の中まで検索できる(タイトル・要約・抄録・著者・雑誌。日本語と英語)。
2. ブラウザが最初に読み込むデータ量と、描画の重さが、件数に比例して増えない。
3. **公開の手順(人の作業)は今と同じにする。** 新しい文献の公開は、これまでどおり
   「3 公開前レビュー作成 → 4 公開反映 → 公開サイトのPRをマージ」で完結し、検索用の作業を人は一切しない。

## 2. 試作で分かったこと(112件、`data/papers.json` の実データ)

| 項目 | 結果 | 設計への影響 |
|---|---|---|
| 日本語検索(そのまま索引) | 「胚細胞腫瘍」が 1件(単純検索なら53件)。複合語が分割され、取りこぼす | **そのままでは使えない。** 下の「2文字ずつ(bigram)」方式にする |
| 日本語検索(2文字ずつの索引 + 検索語を同じ形に変換) | 精巣・腫瘍・胚細胞腫瘍・セミノーマ・シスプラチンなど、単純検索と同数か±1件。**取りこぼしは無し** | 採用。フレーズ指定(引用符)で完全一致に近づく(精巣腫瘍: 3件で一致) |
| 複数の日本語語を同時に指定 | 引用符のフレーズを2つ並べると0件になる | 語ごとに別々に検索して、論文IDの集合で組み合わせる(下の行) |
| 英語検索 | 単語の先頭一致・語幹処理。`nonseminoma` は `seminoma` に一致しない(単純検索では一致) | 「単語」単位の検索として妥当。差は仕様として許容し、テストの基準を単語単位にする |
| 語ごとに検索し、論文IDの集合で AND / OR / NOT を組み合わせる(結果詳細は読まない) | 6通りの検索式(`胚細胞腫瘍 化学療法` / `精巣 OR 卵巣` / `腫瘍 -精巣` / `BEP療法` など)で、単純検索との**差が取りこぼし0件・余分0件** | 採用。検索語の入力形式(3.3)の根拠 |
| 検索1回の転送量 | 初期化 約97KB(検索エンジン本体)。語ごとの索引は数KB。結果1件の詳細は約2.6KB | 件数が増えても、1回の検索で読むのは、その語に関わる分だけ |
| **語を指定しない一覧表示(検索語なし)** | Pagefind は初回に**索引の全ファイル**(112件で10ファイル・約350KB)を読む。絞り込み・並び替えだけでも同じ | **通常の一覧表示は Pagefind に任せない**。軽い一覧データを別に持つ |
| 索引の大きさ | 112件で、索引 356KB + 結果詳細(fragment)288KB(いずれも圧縮済み) | 生成物は公開ブランチに出るだけで、リポジトリには置かない |

## 3. 設計

### 3.1 全体像(元データは `papers.json` のまま)

```
data/papers.json  (元データ。人が触る流れは今と同じ)
      │  デプロイ時に自動生成(コミットしない)
      ├─ search/list.json        軽い一覧(抄録・人向けメモを除く)     ← 一覧・絞り込み・並び替え・ページ分け(常に)
      ├─ search/abstract/<id>.json  抄録(英/日)。カードを開いたときだけ読む
      ├─ search/idmap.json       Pagefindの結果ID → 論文ID の対応表
      └─ pagefind/               検索索引(Pagefind)                    ← 検索語の「語 → 論文ID」の引き当て
```

- `relevance_status = excluded` は、生成時に除外する(今のサイトと同じ扱い)。
- 一覧の1件は約1KB(実測 991バイト、gzip で335バイト)。抄録と人向けメモを分けることで、最初に読むデータは、112件で今の 163KB(gzip)から 38KB(gzip)へ、約2割になる。6,600件でも約2.2MB(gzip、見積もり)。
- 1,000件を超えて `list.json` が重くなったら、年ごとの分割に進める(後述)。

### 3.2 ブラウザの動作(`assets/app.js`)

**Pagefind は「検索語 → 該当する論文IDの集合」を返す部品としてだけ使う。** 絞り込み・並び替え・ページ分けは、
検索語の有無にかかわらず `list.json` に対して今のコードで行う(経路は1つ)。

1. 入力された検索式を、語ごとに分ける(3.3)。
2. 語ごとに Pagefind を1回検索し、結果から論文IDの集合を得る。結果詳細(fragment)は**読まない**。
   Pagefind の結果IDと論文IDの対応表 `search/idmap.json`(ビルド時に生成。112件で約3KB、6,600件で約200KB)を使う。
3. 語の集合を、AND(積)/OR(和)/NOT(差)で組み合わせて、論文IDの集合にする。
4. `list.json` をその集合で絞り、タグ・IF の絞り込みと並び替え、50件ずつの表示は今のコードに任せる。

- 検索の並び順は、選んだ並び替え(発行年など)に従う。Pagefind の関連度順は使わない(語ごとの集合演算のため)。
- カードは今と同じ。抄録は `<details>` を開いたときに `search/abstract/<id>.json` を読む。
- Pagefind を読み込めなかった場合は、`list.json` の範囲(タイトル・要約・著者・雑誌)での部分一致検索に切り替え、
  抄録は対象外である旨を表示する。
- 日本語ページと英語ページで、同じ索引を使う(索引の本文に日英の両方を入れる)。

### 3.3 日本語の扱いと検索式

**索引**: 本文の日本語部分(かな・カナ・漢字)を、重なる2文字ずつの語に分けて入れる(`胚細胞腫瘍` → `胚細 細胞 胞腫 腫瘍`)。
英数字はそのまま(語単位・先頭一致・語幹処理は Pagefind の標準)。

**検索式**(ユーザーが入力する形):

| 書き方 | 意味 | 例 |
|---|---|---|
| 空白(全角も可)で区切る | AND(全部を含む) | `胚細胞腫瘍 化学療法` |
| `OR` または `|` | OR(どれかを含む) | `精巣 OR 卵巣` |
| 語の前に `-` | NOT(その語を含まない) | `腫瘍 -精巣` |
| 日本語と英字の境目 | 自動で別の語に分ける | `BEP療法` → `BEP` と `療法` |

**1つの「語」の中の日本語**は、連続する文字列(順序どおり)に一致させる。具体的には、語ごとに Pagefind へ
`"胚細 細胞 胞腫 腫瘍"` のように、2文字ずつの語を**引用符のフレーズ**として渡す(文字の順序と連続性まで一致する)。
空白区切りの語どうしの組み合わせ(AND/OR/NOT)は、語ごとに別々に検索して、論文IDの集合演算で行う
(Pagefind は1回の検索にフレーズを2つ以上入れられず0件になるため、語ごとに分けて検索する)。

- 変換(2文字語・引用符・語の分割)は、索引の生成側と検索側で**同じ実装を共有**する(食い違うと検索できなくなるため)。
- 1文字だけの日本語の語(`腫` など)は、2文字語が作れない。未決事項(6)。

### 3.4 ビルドとデプロイ(人の手順は変えない)

- 生成スクリプト: `scripts/build_site_search.mjs`(Node)。入力は `data/papers.json`、出力は公開用の一時ディレクトリ。
  Pagefind が書き出した結果ファイル(`fragment/*.pf_fragment`。中身は gzip の JSON)から、結果ID → 論文ID の `idmap.json` も作る。
- Pagefind のバージョンは `package.json` / `package-lock.json` で固定する(検索エンジンと索引の形式がセットで変わるため)。
- `deploy.yml`: `setup-node` → `npm ci` → 生成スクリプトを、既存の JSON 検証の後・公開の前に1工程で追加する。
  生成に失敗したらデプロイも失敗し、**公開中のサイトは前の状態のまま**になる(公開は最後の工程のため)。
- `validate.yml`(PR の検証): 同じ生成と、検索の一致テスト(4.1)を実行する。公開PRの内容が検索を壊さないことが、マージ前に分かる。
- 生成物(`search/`、`pagefind/`)はリポジトリに**コミットしない**。公開ブランチ(gh-pages)にだけ出る。
- 手元で確認する場合: `npm ci && npm run build:search` の後、静的サーバで表示する(手順は `docs/operations/` に追記)。

### 3.5 人の作業(変わる点・変わらない点)

| | 今 | 導入後 |
|---|---|---|
| 公開前レビュー作成 / 公開反映 / PR のマージ | 同じ | **同じ** |
| PR のチェック | JSON 検証・重複ID・テスト | 上に「検索の一致テスト」が加わる(自動) |
| 検索索引の更新 | 不要(全件を読むだけ) | 自動(デプロイ内)。人は何もしない |

## 4. 検証計画

### 4.1 自動テスト(`scripts/check_search_parity.mjs`。CI の validate.yml で実行)

- 現行の単純検索を基準に、Pagefind の結果を比べる。検索語は、(a) 固定の代表語(`tests/search_queries.json`)と、
  (b) データから自動で取り出した頻出語(上位N語)の両方。
- 合格条件:
  - **取りこぼし 0**(基準の結果が、すべて Pagefind の結果に含まれる。英語は単語単位の基準)。
  - 余分な結果(誤ヒット)は、日本語では 0 を目標にする(語ごとのフレーズ一致のため。試作では 0件)。英語は単語単位の差を許容する。
  - 検索式の組み合わせ(AND / OR / NOT)が、基準の集合演算と一致する(試作では6通りで差0件)。
- 変換関数(3.3)の単体テストも入れる。

### 4.2 サイズと速度の予算(同じく CI で警告)

- `list.json`: 1件あたり 1.5KB(現状の約1.5倍)を超えたら警告。
- `pagefind/` の総量と、`init` の転送量を記録し、増え方を PR ごとに確認できるようにする。
- 実装時に、ダミー6,600件でブラウザでの計測(初回表示・検索・もっと見る)を再実施する(ページ分けの計測と同じ手順)。

## 5. 実装ステップ

1. **フェーズ1**: 生成スクリプト(list / abstract / pagefind)と、変換関数、一致テスト。`app.js` は
   `?search=pagefind` を付けたときだけ新方式にする(既定は今のまま)。ダミー6,600件で計測。
2. **フェーズ2**: `deploy.yml` / `validate.yml` に組み込み、公開ブランチのプレビューで実機確認。
3. **フェーズ3**: 新方式を既定にする。今のクライアント側検索は「読み込み失敗時の代替」として残す。

規模の目安は、半日〜1日。各フェーズは main にマージしても、フェーズ2までは公開サイトの挙動が変わらない。

## 6. 既知の制約と未決事項

- **1文字の日本語検索**: 2文字語が作れない。案: (a) 1文字語も索引に入れる(索引が大きくなる)、
  (b) 1文字のときは `list.json` の部分一致に切り替える(抄録は対象外)、(c) 2文字以上を求める旨を表示する。
  お勧めは (b)。
- 英語は単語単位のため、語の途中(`seminoma` で `nonseminoma`)には一致しない。仕様として許容する。
- 語幹処理・前方一致による、意図しない一致が少しある(`nowhere` が `now` を含む文に一致)。許容する。
- `list.json` は件数に比例して増える。約1,000件を超えたら、年ごとの分割と、直近年だけを先に読む方式に進める。
- 公開URLが、サブディレクトリ配下(`/<リポジトリ名>/`)の場合の、`pagefind.js` の読み込みパスは、実装時に確認する(相対パスで読む)。
- Pagefind は、検索語なしの一覧(全件の列挙)が苦手で、今回はそれを避ける設計にしている。将来の Pagefind の版で改善されたら、系統を1つにまとめる余地がある。

## 7. 採用の判断と、やめる場合

- 採用理由: 抄録の中まで検索できる。件数が増えても、1回の検索と描画のコストが一定。公開の手順を変えずに導入できる。
- やめる場合: 索引と `list.json` の生成物は公開ブランチにしか無く、`papers.json` は変わらない。
  `deploy.yml` の1工程と `app.js` の切り替えを戻せば、元の方式に戻る。

## 8. 原因分析と、検討した代替案(2026-10-01 追記)

### 8.1 日本語検索で取りこぼしが出た原因

Pagefind 標準の日本語は、**辞書で単語に分割する方式**だが、分割が文脈で変わる。本文では `…の胚細胞腫瘍…` のように
「胚細胞腫瘍」が1語になる箇所と、`胚細胞 / 腫瘍` に分かれる箇所があり、検索語は1語のまま探す。このため、
同じ語でも、本文の分割と一致した論文(1件)にしかヒットしなかった。HTML ページを索引する通常の使い方でも同じ結果
(胚細胞腫瘍 1件、単純検索 53件)で、組み込み方の問題ではなく、日本語の分割方式の性質によるものだった。

逆に、`化学療法` は 49件(単純検索 37件)と、余分に拾う方向のずれも出た。

### 8.2 「単語ごと」の検索について

- 日本語には空白が無く、単語の境目は辞書で決める。汎用辞書(ブラウザ組み込みの `Intl.Segmenter` で確認)は、
  医学用語で、`セミノーマ` → `セミ | ノーマ`、`縦隔` → `縦 | 隔`、`卵巣奇形腫` → `卵巣 | 奇形 | 腫` のように、不自然に分ける。
  医学辞書つきの形態素解析(Sudachi など)なら精度は上がるが、**検索のたびにブラウザ側でも同じ解析が要る**
  (数MBの辞書と解析器が必要)。静的サイトには重く、辞書の更新も運用に加わる。
- この設計の「語」は、**ユーザーが空白で区切った語**で、AND / OR / NOT は語ごとに効く。
  1つの語の内部は、連続した文字列(順序どおり)に一致させる。日本語の全文検索の標準的な方法(2文字ずつの索引 + フレーズ検索。
  Lucene の CJK bigram、PostgreSQL の pg_bigm など)で、「文字ごとにバラバラに探す」のとは違い、**順序と連続性まで一致する**。
- 辞書ベースの分割と比べた違い: `腫瘍` で `精巣腫瘍` の論文にも一致する(医学検索では望ましい動き)。
  `セミノーマ` を `セミ` と `ノーマ` に分けて、誤って別の語に一致することもない。

### 8.3 Google などの検索エンジンをAPIとして使う案 — 不採用

- **Google Custom Search JSON API**(サイトを検索する公式API)は、2025年に新規受付を終了し、**2027年1月1日に提供終了**と
  案内されている(Google の API 案内、2026年1月)。新規に導入できない。
  [Custom Search JSON API](https://developers.google.com/custom-search/v1/overview) /
  [提供終了の解説](https://brave.com/learn/google-api-shutdown/)
- 仮に使えても、不向き。
  - Google が**クロールして索引した公開ページ**を返す仕組みで、このサイトは1つのページに JSON から描画しているため、
    論文ごとのページが存在せず、抄録の中身は索引されない。反映にも時間がかかる。
  - タグ・IF の絞り込みや、発行年での並び替えと組み合わせられない。
  - 検索のたびに外部へ送信され、利用上限・課金・キーの公開(静的サイトではキーがブラウザに出る)の問題がある。
- 代替の外部サービス(Algolia など、日本語対応の検索SaaS)は、機能は十分だが、**データを外部に預ける**ことになり、
  月額・アカウント管理が運用に加わる。このサイトは、公開データも「本サイトで確認できる範囲」に収めたい方針のため、
  静的ファイルだけで完結する今回の案を優先する。件数が桁違いに増えた場合の将来案として残す。
