# 一覧データの分割(初回の読み込みの高速化)

決定日: 2026-11-01

## 背景
一覧データ(`search/list.json`)は、全件の題名・要約・著者・属性などを1つにまとめていて、約30MB(転送時の圧縮後 約9.5MB)あった。ブラウザは、最初にこれをすべて読み込んでから、カードを出していた。実機で重いという指摘(2026-10-31)があり、測ったところ、初回の表示までの待ちの大半は、このダウンロードだった。内訳は、英語の要約が46%、日本語の要約が14%、属性が10%、題名が10%、著者が7%だった。全文検索(Pagefind)は軽く(1回 0.06〜1MB)、絞り込みのクリックは約0.25秒だった。

## 決めたこと
一覧を3つに分け、順に読む。

| ファイル | 内容 | 圧縮後の大きさ |
|---|---|---|
| `search/head.json` | 既定の並び(発行年の新しい順)の先頭20件。要約・著者つき | 約8KB |
| `search/list.json` | 全件の核(題名・年・タグ・属性・雑誌・IFの階層・PMIDなど)。要約・著者・DOI・URL・抄録を含まない | 約2.1MB |
| `search/details/<n>.json` | 要約・著者・DOI・URL。一覧と同じ順に2,000件ずつ(11ファイル) | 全体で約7.4MB(裏で読む) |

- 読む順: 先頭の20件をすぐに出す → 全件の核が届いたら、絞り込み・並び替え・検索を使えるようにする → 要約・著者を裏で順に読み、届いたカードから埋める(届くまでは「要約を読み込み中…」)。
- 全件の核が届くまでは、絞り込み・IF・並び替えの欄は見えない状態にする(場所は確保し、届いたときに表示が動かないようにする)。その間に検索語を入力すると、全件が届いてから、その語で検索する。
- 絞り込みのURL(`?kubun=…&f_…`)を直接開いたときは、先頭の20件では足りないので、全件の核を待って出す。
- 1文字の日本語の検索と、Pagefind を読めなかったときの代替(要約・著者の部分一致)は、詳細がすべて届くのを待ってから探す。
- 詳細が読めなくても、一覧(核)は使える(要約は「読み込み中」のまま)。
- 一覧は発行年の新しい順に書き出す(画面の既定の並びと同じ。同じ年の中の順は、元の順)。

## 測定(手元のブラウザ。同じ20,168件)
| | 変更前 | 変更後 |
|---|---|---|
| 初回に読むデータ(圧縮後) | 約9.5MB | 約37KB(最初のカード)、約2.1MB(絞り込み・検索が使える) |
| 最初のカードが出るまで(モバイル 6Mbps・CPU 1/4) | ダウンロードだけで約12.6秒 | 約1.4秒 |
| 絞り込み・検索が使えるまで(同上) | 同上以上 | 約4.6秒 |
| 速い回線・PC | 約2.2秒 | 約1.1秒 |

## 注意
- 全体のダウンロード量は、ほぼ変わらない(詳細を後から読むだけ)。初回の体感が軽くなる。
- 論文が増えるほど詳細のファイルが増える(2,000件ごと)。一覧の核は1件あたり約0.5KB(圧縮後 約0.1KB)。
- 確認: `npm run check:split`(分割読み込み)に加え、`check:filter`・`check:attr`・`check:search` も、全件の読み込みを待つ形に直した。

## 追記(2026-11-01): 先頭の件数を100件から20件に
最初に読み込む先頭を、100件から20件にした(ご指示)。1画面に収まる件数だけを先に出し、`head.json` を約37KB から約8KB に減らす。全件の核が届くまでは20件だけを表示する。
